# Constitution

Amendable only by the human maintainer. Agents propose; they do not edit this file.

## 1. Purpose and scope

A gym-session tracker for one household. It records **indoor, equipment-based
strength training only**. It is explicitly *not* a general fitness tracker.

**Out of scope, permanently:** outdoor running, walking, cycling, GPS, route maps,
step counting, calorie/nutrition logging, social feeds, sharing outside the
household, leaderboards, streaks, or any other engagement mechanic.

Rationale: the value of this app is that logging a set is faster than in a
general-purpose app. Every added concept taxes that. If a feature request would
introduce an "activity type" abstraction, the answer is no.

## 2. Product principles

1. **The core loop is sacred.** Logging a set during rest between sets must take
   ≤ 2 taps from app open, with the previous session's values prefilled. Any
   change that regresses this is a bug, regardless of what it adds.
2. **The gym has no signal.** The app is fully functional offline. The local
   database is the source of truth for the UI; the network is a sync detail.
   Never block a UI action on a network call.
3. **Nothing is mandatory.** Wearables, AI coaching, media, and cloud sync are all
   optional. A family member who declines all of them still gets a complete,
   useful app. No feature may hard-depend on another.
4. **Honest data.** Never fabricate, estimate, or interpolate a logged value. If a
   metric is unavailable, show it as unavailable.

## 3. Household and age constraints

- The app serves adults and minors in one household. **Assume minors will use it.**
- No feature may require a Google account, an Apple ID, or any third-party account
  beyond the app's own auth. Health Connect in particular may be unavailable to
  some family members for account-age reasons and **must be treated as absent by
  default** (see `specs/health-connect.md`).
- No advertising, no third-party analytics SDKs, no tracking identifiers, ever.
- Data is visible only within a household. A member cannot see another household's
  data. Enforced at the database layer, not the client (see §5).

## 4. Security

- **No secret ever ships in the app binary.** No LLM API key, no service-role key,
  no admin token. The mobile app holds only the Supabase anon/publishable key,
  which is safe only because RLS is enforced.
- All AI calls go through a server-side Supabase Edge Function. The app calls the
  function; the function holds the model key.
- Secrets in local dev live in `local.properties` (gitignored) or the environment.
  A pre-commit secret scan (gitleaks) runs in CI and must pass.

## 5. Data protection

- **Row-level security is on for every table, with no exceptions.** A table without
  an RLS policy is a production incident. There is a test that asserts this.
- Health metrics read from Health Connect are **aggregated on-device** and only
  session-level summaries (avg HR, max HR, active kcal) are synced. Raw per-second
  samples never leave the phone.
- The user can export everything they have logged and delete their account and all
  its rows. Both are testable requirements, not settings-screen decoration.

## 6. AI conduct

- AI output is **advisory and clearly labelled as generated**. It is never
  presented as fact and never silently writes to the log.
- The coaching feature must not produce medical claims, diagnose, prescribe rehab
  for injuries, or give calorie/weight-loss targets. It suggests exercises, sets,
  reps, and load progression only.
- Given the age constraint in §3: **no body-composition commentary, no weight or
  body-fat goals, no appearance-related language, and no "you should weigh X"
  under any circumstances.** Progression advice is framed in terms of the lift,
  not the body. This is enforced by the Edge Function's system prompt *and* by an
  output filter with tests.
- Suggested load increases are capped (default: ≤ 10% week-over-week per lift, and
  never a suggestion to train through pain). Hard-coded, not left to the model.
- Every AI response is stored with the prompt inputs that produced it, so any bad
  advice can be traced.

## 7. Engineering rules

- **TDD.** Test first, always. See `specs/testing-strategy.md`.
- **Domain layer is pure Kotlin** — no Android imports, no Supabase imports. This
  keeps the iOS port honest and keeps the interesting logic fast to test.
- Dependencies point inward: `ui → domain ← data`. The domain layer knows nothing
  about the layers above or below it.
- No dependency added without an ADR.
- `main` is always releasable. CI must be green to merge.
- Conventional Commits, referencing a user story ID.
